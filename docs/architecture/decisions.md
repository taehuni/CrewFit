# 설계 결정 기록 (ADR)

> 결정은 위에서 아래로 시간순. **확신도 "보통/낮음"은 아직 확인이 남은 항목** — 이후 단계에서 재확인 후 갱신.
> 이전에 구현 코드 없이 합의된 것만 적는다.

---

## D-01. DB/인증은 Supabase, 서버는 Express 유지
- 결정: DB는 Supabase(PostgreSQL), 인증은 Supabase Auth. Express 서버는 없애지 않고 AI 코칭·크루 매칭 등 서버측 로직 담당으로 유지.
- 이유: 2인 팀에서 로컬 MySQL 설치·동기화 마찰 제거. 손으로 짠 bcrypt/JWT를 Supabase Auth가 대체해 코드 감소. Express를 남긴 건 (1) 과제상 백엔드 API 역할이 필요하고 (2) LLM API 키는 서버에만 둘 수 있으며 (3) 매칭 로직은 서버 소관이기 때문.
- 검토했으나 버린 대안: **MySQL 유지** — 로컬 세팅 마찰, 인증 직접 구현 부담. **Supabase 직통(Express 최소화)** — 코드는 가장 적지만 보여줄 백엔드가 얇아지고 RLS 정책 설계 부담이 커짐.
- 확신도: 높음

## D-02. 코스 추천은 Post-MVP
- 결정: 코스 추천(EXT-01)은 MVP에서 제외, 확장 기능으로 분리 관리.
- 이유: 추천에 필요한 경로 데이터가 GPS 트래킹(구현 마지막 단계) 이후에야 쌓임. 2인 15주에 MVP 7개 기능이 이미 빡빡함. "MVP + 향후 확장" 구조가 범위 관리 관점에서도 유리.
- 검토했으나 버린 대안: **MVP 포함** — 데이터 의존성 때문에 어차피 막바지에나 착수 가능, 일정 리스크만 키움.
- 확신도: 높음

## D-03. 기록 모델 원칙 — "구조화할 수 있는 건 구조화, 못 하는 건 메모로 캐치"
- 결정: 모든 활동 기록 = **공통 뼈대**(종목·날짜·소요 시간) + **종목별 구조화 블록**(헬스: 종목×세트×횟수×중량 / 러닝·걷기·자전거: 거리·경로 / 수영: 거리·랩) + **자유 텍스트 메모**. 통계·스트릭은 공통 뼈대와 숫자 필드로만 계산.
- 이유: 서비스가 러닝 전용이 아님(헬스·수영·기타 포함). 사용자가 전문가가 아닐 수 있어 완전 구조화는 진입 장벽. 반면 헬스의 기구·세트·횟수처럼 구조화 가능한 것을 텍스트로 두면 진행 추적이 불가능. LLM 피드백은 메모를 그대로 읽으므로 구조화 범위가 좁아도 품질 손실이 적음.
- 검토했으나 버린 대안: **완전 자유 텍스트** — 제일 단순하나 통계가 "기록 횟수"뿐. **종목별 완전 구조화** — 자유도 요구와 반대, 종목마다 테이블·폼이 늘어 2인 규모에 과함.
- 확신도: 높음

## D-04. MVP 종목 6개
- 결정: 러닝 · 걷기 · 자전거 · 수영 · 헬스 · 기타. "기타"는 공통 뼈대 + 메모만.
- 이유: 러닝만 하는 사람, 헬스만 하는 사람, 수영으로 대체하는 사람을 모두 같은 모델로 수용. 종목이 늘어도 뼈대는 불변.
- 검토했으나 버린 대안: **러닝 단일** — 원래 기획이었으나 사용자 범위가 넓어져 폐기. **종목 무제한 자유 입력** — 구조화 블록을 붙일 대상이 정해지지 않아 D-03과 충돌.
- 확신도: 높음 (목록 자체는 "일단" 확정 — 종목 추가/삭제는 뼈대 변경 없이 가능)

## D-05. 헬스 종목명은 자유 입력 + 자동완성 + 이름 합치기 (마스터 테이블 없음)
- 결정: 종목(기구) 이름은 자유 텍스트로 저장. 자동완성 후보는 **본인 이전 기록 우선 + 클라이언트 정적 시드 목록(흔한 종목 ~30개)**. 저장 시 공백 제거·비교 시 대소문자 무시. 표기가 갈라지면 사용자가 **이름 바꾸기(합치기)** 로 사후 교정(해당 유저의 이름 일괄 UPDATE).
- 이유: 마스터 목록은 관리 주체가 필요한데 2인 팀에 없음. 목록에 없는 기구는 "기타"로 뭉개져 D-03 원칙과 충돌. 자동완성이 첫 화면에 본인 이력을 띄우면 실전에서 표기 흔들림은 거의 발생하지 않고, 발생해도 합치기로 복구 가능. 나중에 마스터 테이블이 필요해지면 이미 저장된 distinct 이름으로 만들면 되므로 전환 비용이 낮음(역방향은 비쌈).
- 검토했으나 버린 대안: **미리 정한 목록 + 기타** — 통계 정확도는 높으나 목록 관리 부담, 누락 종목 처리 문제. **유사도 기반 자동 병합("벤치"≈"벤치프레스")** — 오탐 처리가 더 귀찮고 위 두 장치로 충분.
- 확신도: 높음

## D-06. AI 피드백은 기간 단위 (일간 / 주간 / 월간)
- 결정: 기록 1건마다 피드백을 만들지 않고, 기간(일/주/월) 안의 기록을 모아 한 번에 생성. 결과는 (유저, 기간 종류, 기간 시작일) 단위로 저장. **생성 시점·호출 제한 (단계 4 확정)**: 클라는 피드백 화면을 열 때 `generate`를 호출. 서버는 **최종 프롬프트 문자열 + 모델명의 해시**를 `ai_feedbacks.source_hash`와 비교해 **같으면 LLM 호출 없이 기존 행 반환(즉시)**, 다르면 재생성(입력·템플릿·모델 어느 것이 바뀌어도 자동 반영). 사용자가 "다시 생성"을 누르면 `force: true` — 무조건 재생성, **기간당 3회**(`regen_count`, UX용) 초과 시 429. **비용 상한은 별도**: 실제 LLM 호출 수를 서버 in-memory로 사용자당 분당 5회·일일 20회 제한(force 무관, 데이터 변경으로 해시를 갈아도 걸림). 행에 `llm_calls` 누계를 남겨 사후 집계·상한 조정 근거로.
- 이유: 여러 종목·식단을 함께 보는 종합 피드백이 사용자 요구. 기간 단위 저장만으로는 저장 행이 1개가 될 뿐 버튼 연타마다 LLM 과금(리뷰 지적) → 해시 캐시로 "데이터 안 바뀌면 비용 0 + 화면 즉시 표시", 기록 추가 시 자동 갱신. 해시만 있으면 답이 마음에 안 들어도 영원히 같은 답이고 프롬프트 튜닝 중 재생성도 불가 → force + 횟수 상한. 3회는 임의값, 튜닝 후 조정.
- 검토했으나 버린 대안: **기록 1건당 피드백** — 종목 간 맥락이 끊기고 호출이 기록 수만큼 늘어남. **둘 다** — MVP에 과함. **해시 캐시만** — 재생성 불가. **횟수 상한만** — 데이터가 안 바뀌어도 N번 과금, 화면 열 때마다 대기. **입력 항목을 나열해 해시** — 목록 관리가 생기고 주종목·goal_note 누락(리뷰 지적) → 프롬프트 자체를 해시. **해시 변경 경로도 기간당 N회 제한** — "기록 추가했는데 피드백 못 받음". **`llm_usage` 테이블로 일일 상한** — 정확하지만 테이블·admin 예외·매 호출 DB 왕복, 사용자 수십 명·인스턴스 1개엔 과함 → in-memory, 커지면 교체.
- 확신도: 보통 (제한 규칙은 "일단 이렇게 가고 나중에 수정" — 사용자 결정)

## D-07. 개인화는 프로필의 "주 종목 · 목표"를 프롬프트에 주입
- 결정: 종목별 평가 로직을 따로 만들지 않고, 프로필에 주 종목·목표(예: 체중 감량, 근력) 필드를 두어 LLM 프롬프트에 함께 전달.
- 이유: "헬스만 하는 사람에게 러닝 얘기 안 하기"를 규칙 기반·저비용으로 달성. 종목별 평가 엔진은 2인 규모에 과함.
- 검토했으나 버린 대안: **종목별 평가 로직 분기** — 종목마다 코드가 늘고 유지 부담. **개인화 없음** — 사용자 요구("본인에게 맞게")와 불일치.
- 확신도: 보통 (방식은 합의, 프로필 필드 구성은 단계 3에서 확정)

## D-08. 식단도 D-03과 같은 규칙, 칼로리 DB 연동 없음
- 결정: 식단 = 끼니(공통) + 음식 목록[이름, 양/칼로리는 선택](구조) + 메모(자유). 외부 칼로리 DB 연동은 하지 않음.
- 이유: 운동 기록과 같은 원칙이면 사용자 학습 비용과 구현 비용이 모두 낮음. 칼로리 DB 연동은 범위가 급증.
- 검토했으나 버린 대안: **음식·칼로리·탄단지 완전 구조화 + 외부 DB** — 2인 15주에 과함.
- 확신도: 보통 (원칙은 합의, "음식 목록" 구조 여부는 명시 확인 안 됨)

## D-09. GPS 트래킹은 "야외 종목 기록을 만드는 한 방법"
- 결정: 수동 입력이 기본, GPS 트래킹은 러닝·걷기·자전거 기록에 경로를 붙여 생성하는 선택 경로. MVP 유지. **경로는 이 3종목에만 붙을 수 있음을 DB가 강제** — `activity_routes` INSERT 정책과 `save_tracked_activity`가 부모 `sport`를 검사(헬스·수영·기타 기록에 경로 불가).
- 이유: 서비스가 다종목화되면서 GPS가 유일한 입력 방식일 수 없음. 트래킹 결과가 별도 개념이 아니라 같은 활동 기록이어야 통계·피드백이 일관됨.
- 검토했으나 버린 대안: **GPS 기록을 별도 테이블** — 통계·피드백에서 두 곳을 합쳐야 해 복잡.
- 확신도: 높음 (단계 3에서 사용자 확인 완료. 경로는 별도 테이블 `activity_routes` — D-23)

## D-10. Supabase 접근 경로 — 혼합 (단일 테이블·내 범위 CRUD는 클라 직접, 그 외는 서버)
- 결정: 규칙 **"한 유저 범위의 단일 테이블 CRUD는 클라가 supabase-js로 직접(RLS가 권한), 그 외는 Express 경유"**. 클라 직접: 활동 기록·식단·프로필·피드 글/좋아요/댓글. 서버 경유: LLM 피드백(비밀키), 크루 매칭·가입(다중 테이블·타 유저 데이터), 대시보드 집계, 종목명 합치기(일괄 UPDATE).
- 이유: 팀이 프론트/백으로 갈라져 있어 전부 서버 경유(A)면 프론트가 백엔드 엔드포인트를 기다리는 직렬 구조가 됨. 혼합이면 민규는 CRUD 화면을 Supabase 상대로, 태훈은 서버 로직을 동시에 진행. Express에 남는 일이 전부 "서버만 할 수 있는 동작"이라 산출물로도 설득력 있음. 보안은 RLS를 실제 방어선으로 쓰면 A와 동급이며, RLS는 어느 안이든 써야 함.
- 검토했으나 버린 대안: **전부 서버 경유(A)** — 전통 3계층의 정석이고 검증 일원화·평가 선명도는 높으나, 엔드포인트 25~30개, 2인 직렬화, service_role이 RLS를 우회하므로 핸들러에서 `user_id` 필터를 빠뜨리면 타인 데이터 유출(RLS 안전망 없음). **전부 클라 직접(B)** — D-01에서 "백엔드가 얇아진다"로 이미 폐기.
- 확신도: 높음 (단, "이건 어디?" 판단 규칙을 문서에 명문화하고 지켜야 함 — 위 규칙이 그것)

## D-11. 서버 API는 액션형
- 결정: Express 엔드포인트는 동작을 이름에 드러냄. `POST /api/feedback/generate` · `GET /api/crews/match` · `POST /api/crews/:id/join` · `GET /api/dashboard` · `POST /api/exercises/merge`. 리소스가 실재하는 곳(`crews/:id`)은 명사 유지.
- 이유: D-10으로 서버가 맡는 게 리소스 CRUD가 아니라 "동작" 5~7개. 엄격 REST로 포장하면 매칭·합치기 같은 동작을 명사로 억지 표현해 가독성이 떨어짐. 엔드포인트 이름이 곧 기능 설명이 되는 편이 문서·설명에 유리.
- 검토했으나 버린 대안: **엄격 REST** — 리소스 CRUD가 주 업무일 때 유리하나 지금은 아님. **Postgres 함수(RPC) + Express는 LLM만** — 코드는 최소지만 로직이 SQL로 가서 디버깅·테스트 어렵고, Express가 엔드포인트 1개로 줄어 D-10 취지("보여줄 API")와 충돌.
- 확신도: 높음

## D-12. 인증은 supabase-js 세션 + 서버 토큰 검증, 확인 메일 OFF (MVP)
- 결정: 세션은 supabase-js가 관리(기본 localStorage). 서버는 `requireAuth`에서 `supabase.auth.getUser(token)`으로 검증만. 프로필은 가입 트리거로 생성. MVP는 이메일+비밀번호, **확인 메일 OFF**. **비밀번호 재설정은 구현 ① 인증에 포함**("비밀번호 찾기" 폼 + 메일 링크 착지 페이지 `/reset-password`, 반나절). **카카오 소셜 로그인은 Post-MVP** — `signInWithOAuth` 한 줄이지만 카카오 앱 등록·리다이렉트 URI·가입 트리거의 닉네임 추출 수정이 따라와 배포 주에 끼울 일이 아님.
- 이유: D-10에서 클라가 DB를 직접 만지므로 세션이 클라에 있어야 함 → 서버 대행+httpOnly 쿠키 방식은 구조적으로 불가. 비밀번호 재설정은 "설정"이 아니라 페이지·폼이 있는 작은 기능이라 인증 작업 묶음에 넣는 게 싸다(리뷰 지적으로 정정). 카카오는 데모에 불필요하고 배포 주는 배포만으로도 빠듯함.
- 검토했으나 버린 대안: **확인 메일 ON** — Supabase 기본 발송 시간당 제한이 빡빡해 커스텀 SMTP 필요, 팀원·평가자 테스트마다 메일 확인. **카카오 소셜 로그인 즉시** — 세팅·테스트 시간이 지금 필요 없음, 나중에 추가해도 손해 없음. **서버 대행 + 쿠키** — D-10과 충돌.
- 확신도: 높음

## D-13. 상태 관리 — TanStack Query(서버 데이터) + Context(세션) + 로컬(트래킹·폼)
- 결정: 서버에서 오는 데이터(기록·식단·크루·피드·피드백·대시보드)는 TanStack Query. 세션은 `AuthContext` 하나. 트래킹 중 GPS 좌표·타이머는 그 화면의 `useRef`/`useState`에 두고 종료 시 mutation 한 번으로 저장. 폼은 `useState`. **트래킹 좌표는 전역/Query에 절대 넣지 않음**(초당 갱신 → 앱 전체 리렌더).
- 이유: 이 앱은 서버 데이터 목록·상세 화면 8개가 본체. 로딩/에러/캐시/재조회/무효화를 화면마다 손으로 쓰면 같은 코드의 복사본이 8개. Query는 그걸 "키 + invalidate" 두 개념으로 치환. D-10의 두 경로(Supabase 직접·Express)가 `queryFn` 안에서 똑같은 "프로미스 함수"로 취급되어 화면 코드가 하나로 보임.
- 검토했으나 버린 대안: **React 내장만** — 결국 Query를 손으로 만드는 길. **전역 스토어(Zustand/Redux)에 서버 데이터까지** — 서버 데이터를 복제해 낡음 관리를 직접 해야 하며 이 규모에 과함.
- **캐시 격리 규칙 (사용자 전환 대비)**: 사용자 범위 데이터의 쿼리 키는 **반드시 userId를 포함** — `['activities', userId]`, `['feed', crewId, userId]` 식. 키 생성 헬퍼 하나로 누락 방지. 그리고 `onAuthStateChange`의 `SIGNED_OUT`에서 **`queryClient.clear()`** 로 창고를 통째로 비움. 이유: 같은 브라우저(공용 PC)에서 A 로그아웃 → B 로그인 시, 키에 userId가 없으면 B의 데이터가 오기 전 A의 캐시가 잠깐 표시됨. userId 키가 구조적으로 막고, clear가 메모리 잔존까지 없앰. 둘 다 비용이 한 줄·헬퍼 하나라 둘 다 적용.
- 확신도: 높음 (의존성 1개 추가: `@tanstack/react-query`. 라우팅용 `react-router`도 필수로 추가 예정)

## D-14. 폴더 경계 — 클라 기능별 + shared 승격 규칙 / 서버 routes + services
- 결정: 클라는 `src/features/<기능>/`(auth·activities·tracking·meals·goals·feedback·dashboard·crews·feed·profile — 단계 4에서 goals·profile 추가: goals는 대시보드와 CRUD 화면이 다르고, profile은 D-19·D-25로 편집 화면+회원 페이지가 생김)에 그 기능의 페이지·컴포넌트·쿼리 훅을 모음. `src/shared/`는 **두 기능 이상이 똑같이 쓰는 의견 없는 부품**(버튼·모달·레이아웃·supabaseClient·queryClient)만. 승격 규칙: 처음엔 기능 안에 만들고, 두 번째 기능이 *동일하게* 필요할 때만 shared로 올림. 기능 간 import는 각 기능의 `index.js`가 export한 것만. 서버는 `routes/`(요청 파싱·응답) + `services/`(**Express와 분리된 애플리케이션 로직** — DB·LLM 접근 포함; 순수 계산(매칭 필터·스트릭·프롬프트 조립)은 그 안에서 DB 모르는 함수로 분리해 HTTP 없이 테스트) + `middleware/` + `config/`. controllers 계층 없음.
- 이유: 2인 분업 경계가 폴더로 보여야 서로 안 밟음. 기능 폴더는 "UI 하나"가 아니라 파일 서랍이므로 다른 기능은 데이터 훅만 가져다 쓰고 모양은 각자 그림 — UI 자유도는 종류별 구조와 동일하고 찾기 쉬움만 다름. 서버는 LLM 프롬프트·매칭 규칙을 HTTP 없이 함수로 테스트해야 하므로(CLAUDE.md "피드백 문구 여러 케이스 확인") services 분리. 엔드포인트 7개에 3계층은 과함.
- 검토했으나 버린 대안: **종류별(pages/components/hooks/api)** — 기능 하나 만지면 폴더 4개를 오가고 기능 8개 × 4폴더로 흩어짐. **페이지별 납작** — 파일 하나가 수백 줄. **서버 routes만** — 로직 테스트에 HTTP 필요. **controllers 추가** — 과함.
- 확신도: 높음

## D-15. 서버 권한검사 원칙 — 서버도 기본은 사용자 토큰(RLS 적용), service_role은 열거된 예외만
- 결정: Express는 요청마다 `Authorization` 헤더의 사용자 JWT로 **RLS 적용 클라이언트**(anon 키 + 사용자 토큰)를 만들어 DB에 접근한다. 이것이 기본. `supabaseAdmin`(service_role)은 **다음 두 경우에만**: (1) 사용자 JWT로는 RLS에 걸리는 타 유저 데이터를 **합계로만** 읽는 곳 — 크루 집계 stats(멤버의 crew 공개 기록을 크루 밖에도 합계로 보여줌, private 제외, 개인 행은 반환 안 함 — D-20), (2) 사용자가 직접 쓰지 못하게 RLS로 막아둔 테이블에 서버가 쓰는 곳 — AI 피드백 결과 저장. *(단계 3 수정: 처음엔 "크루 매칭"을 예외 ①로 뒀으나, 크루는 로그인 유저 전원 조회 가능하고 매칭은 내 프로필만 읽으므로 admin 불필요 → 집계로 교체)* `supabaseAdmin`은 `services/` 안의 **열거된 파일에서만 import**하고 `routes/`에서는 금지. 예외를 늘릴 땐 이 목록을 갱신한다.
- 이유: D-10은 "RLS가 실제 방어선"을 근거로 혼합안을 택했는데, 서버가 항상 service_role이면 서버 경로는 그 방어선 밖이다. 핸들러에서 `user_id` 필터를 하나 빠뜨리면(예: 종목명 합치기 UPDATE) 전체 유저 데이터가 바뀐다 — A안을 비판한 바로 그 결함. 사용자 토큰으로 접근하면 같은 실수를 해도 RLS가 "본인 것만"으로 잘라 사고가 나지 않는다. 요청당 클라이언트 생성은 객체 하나라 비용이 없고, 서버 `.env`에 anon 키 추가만 필요.
- 검토했으나 버린 대안: **admin 하나 + 코드 규율**(모든 서비스 함수가 userId를 받아 필터) — 비용 0이지만 규율이 방어선이라 지적된 위험 그대로. **admin 완전 제거** — 매칭·피드백 저장이 RLS에 막혀, 열려면 RLS를 느슨하게 해야 해 본말전도.
- 확신도: 높음 (구현 ⓪에서 `createUserClient(token)` + `supabaseAdmin`으로 분리 완료)

## D-16. 크루 매칭 축 — 종목 · 지역(시/도→시/군/구) · 요일 · 레벨
- 결정: 매칭 축 4개를 `crews`와 사용자 쪽(`profiles`의 `main_sport`·`level`, `user_settings`의 `region_*`·`preferred_days` — D-25)에 같은 의미의 컬럼으로 둠 — `sport`, `region_sido`/`region_sigungu`(고정 목록 = `regions(sido, sigungu)` 테이블, **복합 FK로 시/도-시/군/구 쌍까지 DB 강제**, 드롭다운도 같은 테이블에서 읽음, 시드 ~250행), `activity_days`/`preferred_days`(smallint[] 0~6, DB CHECK로 범위 강제), `level`(beginner/intermediate/advanced). 규칙: `종목 일치(필수) → 시/군/구 일치 → 요일 겹침(배열 &&) → 레벨 일치` 순 필터, 결과 없으면 뒤에서부터 완화. 점수화 없음.
- 이유: 다종목이 되면서 "페이스"는 러닝에만 있는 개념. 레벨은 페이스가 하던 "수준 맞추기"를 모든 종목에 통하는 한 필드로 대체. 지역은 같음 비교라 자유 텍스트 불가 → 고정 목록.
- 검토했으나 버린 대안: **종목+지역+요일(페이스 삭제)** — 수준 미스매치 못 거름. **종목별 조건부 필드(러닝만 페이스)** — 6종목 중 1개 때문에 컬럼·폼·규칙이 조건부. **좌표+반경** — PostGIS급, 코스 추천(EXT-01)에서나 필요.
- 확신도: 높음

## D-17. 크루 멤버십 — 크루별 즉시가입/승인제 선택, MVP 전부 구현
- 결정: `crews.join_mode`(open/approval)를 리더가 생성 시 선택. `crew_members.status`(pending/approved). 리더 1명(`crews.owner_id`), 한 유저 다중 크루 허용, 리더는 탈퇴 불가(크루 삭제만, 양도는 Post-MVP), 리더만 승인·거절·강퇴. 크루 글 작성 권한은 `crew_members.can_post`(기본 false, 리더가 토글 — 단일 행 UPDATE라 클라 직접, RLS가 문지기; 리더는 항상 가능). 승인 흐름(리더 신청 목록·대기 표시·approve/reject)까지 **MVP에 포함**. 리더 멤버십 행(approved·can_post)은 `crews` AFTER INSERT 트리거(security definer)가 자동 생성 — 어떤 경로로 크루를 만들어도 불변식 유지. 리더도 `crew_members`에 행이 있어 멤버 목록·인원수·같은 크루 판정이 한 곳. 리더는 자기 행을 수정·삭제 못 함(항상 approved). 크루 생성은 단일 INSERT라 서버 액션 불필요, 클라 직접(D-10).
- 이유: 사용자 요구. 승인제는 알림 없는 MVP에서 방치 위험이 있으나 리더 크루 페이지 뱃지로 완화. 구현 ③ 일정이 1주→1.5주로 늘어남을 감수.
- 검토했으나 버린 대안: **즉시 가입만** — 단순하나 크루 통제 불가. **스키마만 넣고 승인 UI는 후순위** — 제안했으나 사용자가 MVP 포함 선택. **역할 계층(리더/운영진/멤버)** — 과함; `can_post` 불리언이 필요할 때 `role`로 교체 가능. **리더는 멤버십 행 없이 `owner_id`만** — 멤버 목록·인원수·`shares_crew_with`마다 owner 합집합이 따라다님. **`create_crew` 함수로 트랜잭션** — 함수는 관례일 뿐, 테이블 직접 INSERT로 우회하면 리더 행 없는 크루가 생김(리뷰 지적) → 트리거로 교체.
- 확신도: 높음

## D-18. 피드 — 전체 공개 피드 + 크루 피드, 글 단위 공개 범위·종류·고정
- 결정: `posts.crew_id` nullable(작성자 선택, 달려면 리더 또는 `can_post` 멤버). `visibility`: public(로그인 전원, 전체 피드에도 노출) / crew(승인 멤버만; DB CHECK로 crew_id 필수). `kind`: log(인증)/recruit(모집)/free(자유) — 전체 피드 탭. `is_pinned`: 리더만 true, 크루 피드 상단 고정(별도 "공지" 종류 없음). `sport` 카테고리(첨부 기록→크루 종목→작성자 선택 순 기본값). 기록 첨부 `activity_id` 선택, 경로는 `include_route` 기본 OFF(공개 글에 붙이면 UI 경고). 사진 글당 1장(Supabase Storage). **수정은 작성자만. 크루 리더는 자기 크루 글·댓글 삭제만 가능(운영), 고정은 리더 본인 글만**(공지 = 리더가 쓴 crew 글 + 고정). **크루 삭제 시 태그된 글은 공개 범위 무관하게 함께 삭제**(`on delete cascade`). **좋아요 명단은 글을 볼 수 있는 사람 전원에게 공개**(별도 정책 없이 posts 범위 상속).
- 이유: 자유게시판·크루원 모집 글은 크루 밖에서도 필요. 크루원이라도 크루 이름 없이 쓸 수 있어야 함. 종류 태그가 없으면 인증·모집·자유가 한 줄에 섞여 탭을 못 만듦.
- 검토했으나 버린 대안: **크루 피드만** — 미가입자 활동 불가. **첨부 필수** — "오늘 쉼" 같은 글 불가. **`is_notice` 별도 공지 종류** — 리더의 crew 글 + 고정으로 충분. **리더가 남의 글·댓글 본문 수정** — 운영이 아니라 위조에 가깝고, 남의 글 고정만 허용하려면 OLD/NEW 비교 트리거가 필요 → 삭제만으로 정리(리뷰 지적). **크루 삭제 시 public 글은 태그만 떼고 남김(`set null` + 트리거)** — 크루 이름을 달고 쓴 글은 크루의 것으로 보는 게 맞고, 크루 삭제는 드묾. **좋아요 숫자만 공개** — 노출 범위가 이미 글 범위로 잘려 있어 숨길 이유 없음, 숨기려면 집계 경로가 추가됨.
- 확신도: 높음

## D-19. 프로필 공개 — 기록 3단계(기본 crew) · 크루 목록 불리언 · 회원 페이지 · 경로는 절대 비노출
- 결정: `profiles.activity_visibility`: public(로그인 전원)/crew(같은 크루 승인 멤버)/private(나만), **기본 crew**. `profiles.show_crews` 불리언(기본 true): 같은 크루원에겐 항상, 그 외엔 true일 때만 소속 노출 — 이를 위해 `crew_members` 조회 정책이 이 플래그를 봄(미결 ②의 "멤버 목록 전원 공개"를 이렇게 조정). 회원 페이지 `/users/:id`: 닉네임·주 종목·크루 목록·기록 요약. **GPS 경로는 어느 단계에서도 프로필 경유로 보이지 않음** — 글에 `include_route`로 붙였을 때만(D-23). 글 공개 플래그는 두지 않음(public 글은 정의상 공개, crew 글은 이미 한정).
- 이유: "크루원끼리만"으로 잠그면 크루 밖 동기부여가 사라지고, 전부 열면 낯선 사람에게 위치·습관 노출. 3단계 + 기본 crew면 열고 싶은 사람만 연다. 경로는 위치 이력이라 공개 설정과 무관하게 잠금.
- 검토했으나 버린 대안: **불리언 공개/비공개** — 중간(크루원)이 없음. **기본 public** — 프라이버시 기본값으로 부적절. **기본 private** — 빈 페이지로 시작해 소셜성 상실.
- 확신도: 높음

## D-20. 크루 집계 stats 공개 — 크루 밖 동기부여 경로
- 결정: `GET /api/crews/:id/stats` — 주간 총 거리·총 시간·활동 멤버 수 등 **합계만**. 로그인 유저 전원 조회. 서버 admin으로 집계(D-15 예외 ①): 개인 행은 절대 반환하지 않음. **`private` 기록은 집계에서 제외**("나만"은 합계에도 안 들어감). **기여 멤버 3명 미만이면 통계 비표시** — 2명이면 합계에서 자기 것을 빼 남의 기록이 역산됨(리뷰 지적).
- 이유: "다른 크루 기록 보며 동기부여"에 가장 직접적이면서 개인 프라이버시 부담 0. 크루 밖 동기부여는 이것 + public 개인 기록 + 전체 피드 인증 글 세 경로.
- 검토했으나 버린 대안: 개인 기록을 전부 공개로 여는 것 — 프라이버시. 집계 제외 — 동기부여 경로 약화.
- 확신도: 높음

## D-21. 스트릭은 일 단위, 목표는 `goals` 테이블(제한 없음)
- 결정: 스트릭 = 하루에 활동 기록 1건 이상이면 성공, 연속 일수. 종목 무관, 식단만 기록한 날은 불포함, KST 로컬 날짜(`performed_on`), 오늘은 유예(어제까지 이어졌으면 유지 표시), 소급 입력 반영. 목표 = `goals(type: count/distance/duration, sport: 특정/전체, target, period: week/month)` 여러 개, 개수 제한 없음. 대시보드는 목표별 달성률 바, AI 프롬프트에 목표 주입.
- 이유: 일 스트릭은 습관 지표로 단순·독립. 목표 테이블은 D-03 뼈대(횟수·시간·거리)와 정확히 맞고 다종목을 수용. 주 N회 단일 컬럼으론 "월 러닝 50km + 주 헬스 3회"를 못 담음.
- 검토했으나 버린 대안: **주 단위 스트릭** — 설명 필요, 진행 표시 추가. **`profiles.weekly_goal` 하나** — 얕음. **기한 목표("10월 마라톤")** — 진행률 정의 애매, Post-MVP.
- 확신도: 높음

## D-22. 헬스 세트는 `exercise_sets` 자식 테이블, 종목별 잡값은 `activities.details jsonb`
- 결정: 헬스 = `exercise_sets(activity_id, user_id, exercise_name, set_no, reps, weight_kg)` 한 세트 한 행. `user_id` 비정규화(자동완성·합치기·RLS 단순화, insert 시 부모 소유 검증). 수영 랩·자전거 고도 등 쿼리하지 않는 값은 `details jsonb`. 기록 1행 + 세트 N행 저장은 Postgres 함수 `save_gym_activity`로 트랜잭션.
- 이유: D-05 요구 셋(자동완성 DISTINCT, 이름 합치기 UPDATE, 중량 추이 GROUP BY)이 전부 단순 SQL. jsonb면 경로 조작 UPDATE·`jsonb_array_elements` 이중 전개로 셋 다 어려워짐.
- 검토했으나 버린 대안: **`details jsonb` 안에 배열** — 저장 한 번이지만 D-05가 전부 어려움.
- 확신도: 높음

## D-23. GPS 경로는 `activity_routes` 별도 테이블
- 결정: `activity_routes(activity_id PK, points jsonb)`. 조회 정책: 본인이거나, `include_route=true`인 **볼 수 있는 글**에 첨부됐을 때만. 프로필 공개 설정(D-19)은 이 테이블에 영향 없음.
- 이유: RLS는 행 단위라 "기록은 보이되 경로 컬럼만 숨김"을 한 테이블에서 못 함. 분리하면 "경로는 글 첨부 시만"이 DB에서 강제됨. 부수 효과로 activities 행이 가벼워짐(경로 jsonb가 큼).
- 검토했으나 버린 대안: `activities.route` 컬럼 — 프로필 public이면 경로까지 노출, 뷰/컬럼 권한으로 우회하면 supabase-js 경로가 복잡.
- 확신도: 높음

## D-24. 스키마·RLS 공통 원칙 (전문: [`schema.md`](schema.md))
- 결정: (1) enum 대신 `text + CHECK` — 값 변경이 ALTER 한 줄. (2) 모든 테이블 RLS ON, `to authenticated` 명시(anon 차단). (3) INSERT/UPDATE는 반드시 `with check`, UPDATE는 `using`도. (4) `auth.uid()`는 `(select auth.uid())`로 감싸 행마다 재평가 방지. (5) `crew_members`를 참조하는 정책은 `security definer` 헬퍼(`is_crew_owner`, `is_crew_member`, `can_post_in_crew`, `shares_crew_with`) 경유 — 자기 참조 재귀 방지, `anon` 실행 권한 회수. (6) 자식 테이블 조회는 `exists (select 1 from 부모 where id = …)`로 부모 RLS를 그대로 상속. (7) 정책마다 "막는 공격" 주석 1줄. (8) 미래 확장(매너 점수·이행 점수 등)은 컬럼 추가 또는 별도 테이블 + 집계로 — `extra jsonb` 통은 두지 않음. (9) **식별 컬럼(`id`·`user_id`·`author_id`·`crew_id`·`owner_id`·`created_at`)과 `activities.sport`는 생성 후 불변** — RLS는 "어느 행"만 정하므로 "어느 컬럼"은 `authenticated`의 UPDATE 권한을 회수하고 바뀌어도 되는 컬럼만 컬럼 단위 GRANT. (10) ADR의 값 범위·필수 여부·행 간 관계는 전부 DB 제약으로 — 함수 경로만 믿지 않음(`duration_sec not null`, 요일 배열 `<@ '{0..6}'`, `posts.image_path`는 작성자 폴더 CHECK, `exercise_sets`는 부모 `sport='gym'`만, `exercise_name` trim CHECK + `lower()` 유니크 인덱스). (11) `updated_at`은 테이블마다 BEFORE UPDATE 트리거, 다중 테이블 저장은 `security invoker` 함수로 트랜잭션(`save_gym_activity`, `save_tracked_activity`) — 클라가 두 번 INSERT하는 경로는 두지 않음. (12) 클라 입력으로 유니크 키가 결정되는 값(피드백 `period_start`)은 서버가 정규화하고 DB CHECK가 재검증. (13) 개인 행이 RLS로 숨겨지는 테이블의 **개수**가 필요하면 security definer 집계 함수(`crew_member_count`)로 — JWT로 세면 틀린 수가 나옴. (14) SQL 문서는 ① 테이블 → ② 함수 → ③ 정책 → ④ 트리거·권한 → ⑤ storage 순 — Postgres가 함수·정책 생성 시 참조 테이블 존재를 검사하므로 이 순서가 곧 마이그레이션 순서.
- 클라 직접 테이블: profiles, user_settings, activities, activity_routes, exercise_sets, meals, goals, posts, post_likes, comments, regions(읽기), crews(생성 시 트리거가 리더 행 생성), crew_members(읽기·탈퇴·강퇴), storage `post-images`(비공개 버킷, D-26). 서버 액션(사용자 JWT): 크루 가입·승인·거절, 매칭, 대시보드, 종목명 합치기. 서버 admin: ai_feedbacks 쓰기, 크루 집계.
- 이유: 클라가 DB를 직접 만지는 D-10 구조에선 RLS가 실제 보안선이고, 서버도 사용자 JWT(D-15)로 접근하므로 같은 정책이 양쪽 권한 규칙. 초안이라 자주 바뀔 것을 전제로 변경 비용이 낮은 선택(text+CHECK, 좁은 테이블).
- 검토했으나 버린 대안: Postgres enum — 값 삭제 불가. 정책에서 `crew_members` 직접 서브쿼리 — 무한 재귀. `extra jsonb` — 타입·검증·RLS·쿼리 전부 흐려짐.
- 확신도: 높음 (초안. 구현 중 정책 수정 시 이 문서와 schema.md를 함께 갱신)

## D-25. 프로필은 공개 카드(`profiles`)와 비공개 설정(`user_settings`)으로 분리
- 결정: `profiles` = 로그인 전원이 읽는 값(닉네임·주종목·레벨·`activity_visibility`·`show_crews`). `user_settings`(1:1, 본인만 읽기/수정) = 지역 시/도·시/군/구, 선호 요일, 목표 메모. 가입 트리거가 두 행을 함께 생성. 매칭(`/api/crews/match`)은 사용자 JWT로 본인 `user_settings`만 읽으면 되므로 서버 예외 불필요.
- 이유: RLS는 행 단위라 한 테이블에서 "닉네임은 보이고 동네는 숨김"이 불가능. 리뷰에서 `region_sigungu`·`preferred_days`·`goal_note`가 로그인 전원에게 노출됨이 지적됨. `activity_visibility`·`show_crews`는 activities·crew_members 정책이 서브쿼리로 읽어야 해서 공개 쪽에 남김(남이 알아도 되는 플래그).
- 검토했으나 버린 대안: **`profiles`를 본인만 읽기로 잠그고 `public_profiles` security definer 뷰** — Supabase 린트 경고 대상이고, profiles를 서브쿼리하는 기존 정책이 깨져 헬퍼가 추가로 필요. **컬럼 단위 SELECT GRANT** — 본인 행의 비공개 컬럼을 읽을 별도 경로(함수/뷰)가 또 필요.
- 확신도: 높음

## D-26. 게시글 사진은 비공개 버킷, storage 정책이 posts 가시성을 상속
- 결정: 버킷 `post-images`는 `public = false`. `storage.objects` select 정책: 내 폴더이거나 `exists (select 1 from posts where image_path = name)` — 서브쿼리에 posts RLS가 적용되어 **내가 볼 수 있는 글의 사진만** 보임. 업로드/삭제는 내 폴더(`{auth.uid()}/…`)만. 클라는 `createSignedUrls`(배치)로 URL을 받고, 서명 시점에 정책이 평가됨. `posts.image_path`에 부분 인덱스.
- 이유: 리뷰 지적 — 읽기가 로그인 전원에게 열려 있어 크루 전용 글 사진이 크루 밖에서도 보였고, "경로 UUID를 모름"은 권한검사가 아님. 가시성 규칙이 posts 한 곳에만 있게 유지.
- 검토했으나 버린 대안: **서버가 서명 URL 발급** — 피드 페이지마다 서버 왕복 + D-15 admin 예외 추가. **공개 버킷 유지** — 위 이유로 불가.
- 확신도: 높음 (글 저장 전 업로드만 하고 버린 고아 객체 정리는 Post-MVP)
